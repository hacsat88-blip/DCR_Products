# Parallel Execution Rules — 並列実行の判断基準

> deploy.ps1: `_` プレフィックスのため deploy 対象外（参照ドキュメント）

## 概要

`ulw` (超並列処理) およびサブエージェントの使用は、要件を満たす場合のみ許可する。
誤った並列化は競合・不整合・デバッグ困難を招く。

判断の優先順位：**安全 ＞ 目的達成 ＞ 速度 ＞ 完全性**

---

## 並列実行の使用条件（すべて満たす場合のみ）

以下の **4 条件をすべて**満たす場合に並列実行を選択する:

| 条件 | 確認方法 |
|------|----------|
| **独立タスクが 3 つ以上**存在する | タスクリストを作成して数える |
| **タスク間にデータ依存がない** | A の出力が B の入力にならないことを確認 |
| **各タスクが原則 1 ファイル以内**の変更に収まる | スコープを事前に確定する |
| **全タスクが P1 または P2**である | P3 が含まれる場合は逐次処理に切り替え |

---

## 並列禁止条件

以下のいずれかに該当する場合は**逐次処理のみ**:

| 禁止条件 | 理由 |
|----------|------|
| P3 操作を含む | 承認フローが必要なため並列化不可 |
| テスト実行 → その修正 | 結果を見てから次手を決めるため |
| 共有状態への同時書き込み | 同一ファイル・設定・DB への競合 |
| `gate-state.json` の変更を伴う | ゲート状態は逐次管理が必須 |
| デバッグサイクル | 原因→修正→検証のチェーンは直列 |
| API 設計変更 | 型の波及を追跡するために直列が必要 |

---

## 逐次処理が優先されるユースケース

- **デバッグ**: 原因特定 → 修正 → 検証（各ステップが前の結果に依存）
- **リファクタリング**: 依存順序が重要（下位から上位へ）
- **API 設計変更**: 型変更の波及を段階的に追跡
- **データベースマイグレーション**: 順序が保証されなければ整合性が壊れる
- **CI/CD パイプライン変更**: 段階的に検証しながら進める

---

## 並列実行のベストプラクティス

並列化する場合:

1. **事前にタスクを列挙**し、依存関係を明示する
2. **各タスクのスコープを 1 文で定義**する（曖昧なタスクは並列化しない）
3. **合流ポイントを定義**する（どこで結果をまとめるか）
4. **失敗時の対応を決める**（1 タスク失敗で全体をロールバックするか）

```
ulw 使用例:
  並列タスク A: _quality-floor.md を作成する
  並列タスク B: _self-correction.md を作成する
  並列タスク C: _auto-escalation.md を作成する
  合流: 3 ファイルを同一コミットにまとめる
```

## サブエージェント vs 直接処理

| 状況 | 推奨 |
|------|------|
| 調査が必要な大規模コードベース探索 | Explore サブエージェント |
| 既知のファイルへの書き込み | 直接処理（Agent 不要） |
| 独立した実装タスクが 3+ | subagent-driven-development |
| 1〜2 の実装タスク | 直接処理 |
| 不確実な範囲の調査 | Explore × 1〜3（並列可） |
