# Auto-Escalation Rules — P2 → P3 自動昇格

> deploy.ps1: `_` プレフィックスのため deploy 対象外（参照ドキュメント）
> inherits: coding-standards

## 概要

P2 として開始した操作が以下の条件に該当する場合、P3 として再分類し自動停止する。
承認なしに P3 相当の影響を与える変更を行うことを防ぐ。

判断の優先順位：**安全 ＞ 目的達成 ＞ 速度 ＞ 完全性**

---

## P2 → P3 自動昇格条件

以下のいずれかに該当する操作は自動的に P3 へ昇格する:

| 条件 | 具体例 |
|------|--------|
| 単一操作で **5 ファイル以上**を変更する | リネーム、一括置換、大規模リファクタリング |
| **依存関係ファイル**に波及する変更 | `package.json`, `requirements.txt`, `go.mod`, `Cargo.toml` |
| **外部サービス接続設定**を含む変更 | API エンドポイント、認証設定、DB 接続文字列 |
| 同セッション内で **PostToolUseFailure が 2 回以上**発生した操作の再試行 | 失敗パターンの繰り返し |
| `_permissions.md` の **Mechanical P3 patterns** に一致するファイル | `*.config.*`, `tsconfig*`, `.env*`, `Dockerfile*` など |
| **本番環境**または**共有インフラ**に影響する変更 | 本番 DB、CI/CD パイプライン、共有 API キー |

---

## 昇格時の必須アクション

P3 昇格を検出したら:

1. **即座に停止** — 作業を中断し、ユーザーに報告する
2. **影響範囲の要約** — 3 行以内で変更内容・影響ファイル・リスクを説明する
3. **代替案の提示** — より安全なアプローチを 1 つ提案する
4. **明示的承認を待つ** — 承認なしに継続しない

```
🔴 P3昇格: [操作の概要]
影響: [ファイル数] ファイル / [リスク概要]
代替案: [安全な代替アプローチ]
続行するには承認が必要です。
```

---

## 昇格後の許可フロー

ユーザーが承認した場合:
- `gate-state.json` の `plan_passed: true` を前提として実行する
- 実行後に「何を / なぜ / 結果」を短く報告する（P2 の事後報告義務）

ユーザーが拒否した場合:
- 代替案を実行するか、タスクを中断する
- 中断理由を明示する

---

## 例外

以下は P3 昇格対象外（設計上安全と判断されるもの）:

- `docs/` 以下の Markdown ファイル（コードに影響しない）
- `*.test.*` / `*.spec.*` ファイルのみの変更（本体コードに影響しない）
- `.gitignore` への追加（削除・変更は除く）
- READ-ONLY な操作（ファイル読み取り、検索、差分確認）
