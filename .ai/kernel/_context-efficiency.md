# Context Efficiency Rules — トークン効率と Compact 戦略

> deploy.ps1: `_` プレフィックスのため deploy 対象外（参照ドキュメント）

## 概要

コンテキスト窓は有限のリソース。効率的な使用がセッション品質を左右する。
読み込む前に「本当に必要か」を判断し、圧縮のタイミングを逃さない。

---

## Token Budget 意識

### ファイル読み込み前の判断

| 状況 | 判断 |
|------|------|
| ファイルの特定箇所が必要 | `offset` + `limit` で部分読み込み |
| ファイル全体が必要 | 全読み込みを行う（上限 2000 行） |
| 複数ファイルの特定箇所 | Grep で該当行を先に特定してから Read |
| 調査目的で内容不明 | まず Glob/Grep で概観 → 必要なファイルのみ Read |

### 禁止パターン

- 同一ファイルを 3 回以上 Read する（キャッシュせずに繰り返す）
- 変更不要のファイルを確認目的で全体読み込みする
- `find` / `ls -R` の代わりに Glob を使わない

---

## Compact 推奨条件

以下のいずれかに該当したら、コンテキスト圧縮を検討する:

1. **会話ターン数が 20 を超えた**場合
2. **同一コンテキストを 3 回以上参照**した場合（関数定義、仕様など）
3. **ツール呼び出し失敗が 3 回連続**した場合（デバッグサイクルが長期化）
4. **plan フェーズ完了後**、implementation フェーズに移行する直前

---

## 圧縮前の必須アクション

Compact 前に以下を実行し、重要情報を永続化する:

```
① plan ファイル保存: docs/dcr/plans/YYYY-MM-DD-<feature>.md
② gate-state 記録:   .ai/kernel/gate-state.json (Update-GateState 呼び出し)
③ メモリ記録:        mem_cli.py quick-save で重要な発見・決定を保存
④ タスクリスト確認:  未完了タスクの状態を確認してからコンテキスト解放
```

圧縮後に継続できる状態を作ってから圧縮する。圧縮でコンテキストを失っても
`gate-state.json` と `docs/dcr/plans/` で作業状態を復元できる。

---

## 大量ファイル処理のガイドライン

| ファイル数 | 推奨アプローチ |
|-----------|----------------|
| 1〜3 ファイル | 直接処理 |
| 4〜10 ファイル | 並列処理 (ulw) を検討 |
| 11 以上 | バッチ分割 + plan ファイルに進捗記録 |

並列処理の判断基準は `_parallel-execution.md` を参照。

---

## セッション効率の指標

セッション内で以下を意識する:

- **Read > Edit の比率**が 3:1 を超えたら調査過多（実装に移行する）
- **同一エラーを 2 回以上**見たら原因特定を優先（試行錯誤ループに入っていない）
- **"確認のための確認"** は行わない（既に読んだファイルは記憶を信頼する）
