# Tools

Utility scripts for build, deployment, and maintenance operations.

## Core Scripts

### `deploy-all.ps1` (Orchestrator)

**Purpose:** Unified deployment coordinator for all environments

**Delegates to:**
- `manifest-compiler.ps1` (frontmatter → JSON manifest)
- `adapters/vscode.ps1` → `.github/copilot-instructions.md`
- `adapters/claude.ps1` → `CLAUDE.md`
- `adapters/codex.ps1` → `AGENTS.md`
- `adapters/agents.ps1` → `.codex/agents/*.toml` + `.claude/agents/*.md` (Git 管理外)

**Usage:**
```powershell
.\deploy-all.ps1                    # Deploy to all targets
.\deploy-all.ps1 -Target vscode     # Deploy to VS Code only
.\deploy-all.ps1 -Target agents     # Generate Codex/Claude agent mirrors only
.\deploy-all.ps1 -DryRun            # Preview without executing
```

**Related:** `deploy.ps1` (root) delegates to `deploy-all.ps1`

---

### `manifest-compiler.ps1`

**Purpose:** Compile frontmatter from `.ai/catalog/rules/*.md`, `.ai/catalog/skills/*/SKILL.md`, and `.ai/catalog/agents-source/` into a unified JSON manifest

**Input:** YAML frontmatter with `targets: [vscode, claude, codex]` field

**Output:** `manifest.json` (generated artifact, not versioned)

**Usage:**
```powershell
.\tools\manifest-compiler.ps1 -RepoRoot . -OutputPath ./manifest.json
```

**Schema:** See `lib/manifest.schema.json`

---

### `adapters/` (Per-Environment Converters)

Each adapter reads `manifest.json` and generates tool-specific formats:

#### `adapters/vscode.ps1`
Generates `.github/copilot-instructions.md` for VS Code Copilot

#### `adapters/claude.ps1`
Generates `CLAUDE.md` for Claude Code environment

#### `adapters/codex.ps1`
Generates `AGENTS.md` for Codex (GitHub CLI) environment

#### `adapters/agents.ps1`
Generates `.codex/agents/*.toml` and `.claude/agents/*.md` from `.ai/catalog/agents-source/`.
The generated agent mirrors are ignored by Git; edit `.ai/catalog/agents-source/` instead.

## Utility Scripts

**Called by:** `validate.ps1`

**Usage:**
```powershell
.\tools\generate-routing-index.ps1
```

### `audit-openai-skills.ps1`

**Purpose:** Compare DCR `.ai/catalog/skills/` against the local OpenAI official skills baseline and classify slimming candidates.

**Input:** `.ai/catalog/skills/`, OpenAI curated plugin cache, OpenAI primary runtime skills, and local system skills.

**Output:** Read-only console report by default; JSON when `-AsJson` is provided. The report
includes reviewed exact-overlap decisions, deprecated pipeline aliases, and deprecated growth /
documents / governance umbrella aliases so same-name OpenAI skills and consolidated local skills are
not treated as automatic replacement/deletion candidates.

**Usage:**
```powershell
.\tools\audit-openai-skills.ps1
.\tools\audit-openai-skills.ps1 -ShowCandidates
.\tools\audit-openai-skills.ps1 -AsJson
```

### `router-decisions-report.ps1`

**Purpose:** Show a compact status report from `.ai/kernel/router-decisions.jsonl`

**Input:** Router decision JSONL generated by `Write-RouterDecision`

**Output:** Console summary of `proposed / approved / rejected / executed`, pending approvals, cognitive-load rates, top candidates, rejected candidates, proposal-state transitions, stale proposal diagnostics, and up to 3 reduction suggestions

**Usage:**
```powershell
.\tools\router-decisions-report.ps1
.\tools\router-decisions-report.ps1 -OutputJson .\docs\router-decisions-summary.json
.\tools\router-decisions-report.ps1 -TopN 5 -StaleHours 12
.\tools\router-decisions-report.ps1 -GateStatePath .\.ai\kernel\gate-state.json
```

**V3 cognitive-load check:** use this as the standard routing visibility smoke path.

```powershell
powershell.exe -NoProfile -File .\tools\router-decisions-report.ps1
powershell.exe -NoProfile -File .\tools\test-router-decisions-report.ps1
```

Look for `Cognitive load`, `Stale proposal`, and `Next reduction suggestions`. Keep console output short; use `-OutputJson` when detailed ranked data is needed. The test script is also part of `validate.ps1`.
Reduction suggestions ignore smoke/test/fixture telemetry by default and return `collect_real_usage` until enough non-synthetic routing decisions exist.

**V7 reduction advisor:** use this when deciding what to reduce next. It is advisory only and never deletes files or marks assets deprecated. Synthetic smoke/test/fixture decisions are ignored by default so validation telemetry does not drive catalog pruning.

```powershell
powershell.exe -NoProfile -File .\tools\reduction-advisor.ps1
powershell.exe -NoProfile -File .\tools\reduction-advisor.ps1 -OutputJson .\docs\reduction-advisor.json
powershell.exe -NoProfile -File .\tools\test-reduction-advisor.ps1
```

Actions are `collect_real_usage`, `remove_later`, `bundle_into_hub`, `expose_underlying_asset`, `clarify_trigger`, `observe_more`, and `no_action`. Actual removal or deprecation belongs to a later approved change. `expose_underlying_asset` is used when `pied-piper` is visible too often as the coordinator; it means reveal the selected rule/skill/agent behind it, not remove the coordinator. Use `-IncludeSynthetic` only when debugging the test harness itself.

**V7.1 shadow routing trial:** use this during real work to collect lightweight routing feedback before any deletion, deprecation, or display suppression.

```powershell
powershell.exe -NoProfile -File .\tools\shadow-routing-trial.ps1 `
  -InputText "サトシ開発目線で軽く見て" `
  -Kind agent -Name pied-piper `
  -Status approved -UserReplyType approve `
  -UserJudgement just_right -ActualAsset "agent:pied-piper"
powershell.exe -NoProfile -File .\tools\test-shadow-routing-trial.ps1
```

Recommended `-UserJudgement` values are `just_right`, `too_many`, `off_target`, `lighter`, `too_heavy`, and `unclear`.

**V8 display policy advisor:** use this after several shadow trials exist. It converts user feedback into display-only actions such as suppressing secondary options, showing the underlying asset behind `pied-piper`, or making the lightweight path the default. It never deletes files, marks assets deprecated, or changes routing by itself.

```powershell
powershell.exe -NoProfile -File .\tools\display-policy-advisor.ps1
powershell.exe -NoProfile -File .\tools\display-policy-advisor.ps1 -OutputJson .\docs\display-policy-advisor.json
powershell.exe -NoProfile -File .\tools\test-display-policy-advisor.ps1
```

Actions are `collect_shadow_trials`, `suppress_secondary_options`, `show_underlying_asset`, `make_lightweight_default`, `demote_candidate`, `clarify_display_copy`, `keep_as_default`, and `no_display_change`. Treat them as proposal material for the next approved routing change, not as automatic edits.

**V9 display policy proposal:** use this to convert V8 advice into a short approval proposal. Preview is default; `-CommitState` stores the proposal in `.ai/kernel/gate-state.json` so the next natural-language reply can be resolved by the proposal state machine.

```powershell
powershell.exe -NoProfile -File .\tools\display-policy-proposal.ps1
powershell.exe -NoProfile -File .\tools\display-policy-proposal.ps1 -CommitState
powershell.exe -NoProfile -File .\tools\test-display-policy-proposal.ps1
```

The proposal uses `approve_required` because display policy changes alter the routing experience. Approval records the chosen option; actual implementation still belongs to a later approved change.

**V10 bundle advisor:** use this to find candidates that should be shown under a parent hub rather than as separate visible choices. It reads routing decisions and catalog frontmatter, then emits advisory actions only.

```powershell
powershell.exe -NoProfile -File .\tools\bundle-advisor.ps1
powershell.exe -NoProfile -File .\tools\bundle-advisor.ps1 -OutputJson .\docs\bundle-advisor.json
powershell.exe -NoProfile -File .\tools\test-bundle-advisor.ps1
```

Actions are `collect_bundle_evidence`, `bundle_into_hub`, `expose_underlying_asset`, `clarify_parent_label`, `keep_separate`, and `observe_more`. V10 never deletes, deprecates, or physically merges assets; it only prepares bundle evidence for a later approval proposal.

**V10.1 bundle proposal:** use this to convert V10 bundle advice into a short approval proposal. Preview is default; `-CommitState` stores the proposal in `.ai/kernel/gate-state.json` so the next natural-language reply can be resolved by the proposal state machine.

```powershell
powershell.exe -NoProfile -File .\tools\bundle-proposal.ps1
powershell.exe -NoProfile -File .\tools\bundle-proposal.ps1 -CommitState
powershell.exe -NoProfile -File .\tools\test-bundle-proposal.ps1
```

The proposal uses `approve_required` because bundling changes visible routing choices. Approval records the chosen option; actual implementation still belongs to a later approved change.

## Library

### `lib/manifest.schema.json`

JSON Schema for validating manifest structure. Used by:
- `manifest-compiler.ps1` (output validation)

## Adding New Tools

1. Create `tools/<new-name>.ps1`
2. Document in this README under appropriate section
3. If it's a deployment adapter, add to `adapters/` and register in `deploy-all.ps1`
4. Update `validate.ps1` if the script should be tested
5. Add to version control: `git add tools/<new-name>.ps1`
